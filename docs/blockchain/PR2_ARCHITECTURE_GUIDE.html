01 · 먼저 이해할 것

이번 PR이 만든 세 가지 약속

블록체인의 복잡한 용어를 잠시 내려놓으면, 이번 변화는 다음 세 문장으로 요약됩니다.

01

모든 노드가 같은 거래를 실행한다

제안 블록에 들어 있는 정확한 payload만 실행합니다. 각 노드의 로컬 메모리 상태로 빈칸을 추측하지 않습니다.

02

합의한 결과를 재시작 후에도 증명한다

상태·영수증·합의 안전정보를 RocksDB에 묶어서 기록하고, 복구 시 같은 hash가 나오는지 다시 확인합니다.

03

Canonical 거래의 “접수”와 “확정”을 구분한다

주문·trigger API는 먼저 pending을 알리고, 합의와 디스크 저장이 끝난 뒤에만 finalized 영수증과 알림을 제공합니다.

비유: 이전에는 접수 창구, 심사실, 장부가 서로 다른 복사본을 볼 수 있었습니다. 지금은 하나의 원본 문서가 접수 → 심사 → 도장 → 금고 보관을 순서대로 통과합니다.

03 · 거래 한 건 따라가기

주문 버튼을 누른 뒤 “확정”되기까지

이 흐름을 이해하면 canonical 서명, gossip, QC, root, receipt가 왜 필요한지 한 번에 연결됩니다.

1

지갑이 정확한 행동에 서명

프론트는 주문·취소·포지션 종료·TP/SL을 canonical EIP-712 v1 envelope으로 만듭니다.

왜? 다른 체인에서 서명을 재사용하거나, 서명 뒤 행동을 바꾸는 것을 막습니다.

2

Canonical 주문·trigger API가 입구에서 검증

chain domain, signer, nonce, 유효시간, action hash와 크기를 확인한 뒤 mempool에 넣고 {status: "pending", tx_hash}를 반환합니다.

의미: pending은 “접수됨”이지 “체인에 확정됨”이 아닙니다.

3

validator 네트워크로 전파

첫 gossip이 끊겨도 2초마다 최대 32건·2 MiB 범위에서 미확정 envelope을 재전파합니다.

왜? 거래를 받은 노드가 현재 leader가 아니거나 순간적으로 연결이 끊긴 경우를 복구합니다.

4

leader가 결정적인 순서로 블록 제안

우선순위 bucket을 사용하되, 같은 signer의 nonce는 반드시 끊김 없이 순서대로 배치합니다.

왜? 미래 nonce는 기다릴 수 있지만, 합의 실행 순서는 모든 노드에서 같아야 합니다.

5

모든 validator가 독립 실행

부모 block, proposer, QC, payload를 검증한 뒤 private candidate 상태에서 같은 거래를 실행합니다.

왜? leader의 결과를 믿는 것이 아니라 각 노드가 직접 계산해 확인합니다.

6

두 개의 결과 지문 생성

app_hash는 최종 상태, commitment_root는 거래 영수증과 이벤트의 지문입니다.

왜? “잔액이 무엇인가”와 “이번 블록에서 무슨 일이 있었나”를 각각 검증합니다.

7

stake-weighted BLS 투표와 QC

현재 위원회의 voting power가 엄격한 2/3 초과에 도달하면 QC(정족수 인증서)가 만들어집니다.

비유: QC는 충분한 지분을 가진 검증자들이 같은 문서에 찍은 압축 공증 도장입니다.

8

HotStuff-2 two-chain finality

인증된 자식 block까지 연결되면 적절한 조상 block이 되돌릴 수 없는 확정 상태가 됩니다.

왜? 단지 제안되거나 한 번 투표된 상태를 확정이라고 부르지 않습니다.

9

RocksDB에 원자적으로 기록

block, 높이 index, 합의 safety state, roots, receipts/events, commit marker를 동기화된 batch로 저장합니다.

왜? 중간에 전원이 꺼져도 절반만 저장된 “유령 확정”을 만들지 않습니다.

✓

사용자에게 finalized 공개

GET /api/v1/transactions/:tx_hash 조회와 private WebSocket transactionFinalized 알림이 이 시점에만 나갑니다. Non-dev 정책에서는 private 구독 서명이 필수이고, 현재 dev fixture에서는 인증을 생략할 수 있습니다.

결과: 알림을 놓쳐도 영구 receipt index에서 다시 조회할 수 있습니다.

Canonical 경로의 범위: 위 흐름은 서명된 주문·취소·trigger·position-close 경로를 설명합니다. Dev-only simulated deposit/withdraw와 일부 legacy route는 아직 이 pending tx-hash 계약을 사용하지 않으며, mainnet 자산 경로로 간주하면 안 됩니다.

기술 상세: canonical EIP-712 envelope에 무엇이 들어가나?

chainDomain, signer, nonce, validAfter, validUntil, actionHash가 서명 대상입니다. chainDomain은 단순 EVM chain ID가 아니라 genesis와 protocol 설정에 묶인 hash입니다.

같은 envelope을 API ingress, mempool, block 실행, validator replay에서 반복 검증합니다. 프론트와 Rust는 golden vector 테스트로 동일한 action encoding을 확인합니다.

04 · 합의와 상태 무결성

블록에는 결과를 증명하는 두 개의 봉인이 있다

모든 상태를 한 덩어리로 취급하지 않고, “현재 상태”와 “이번 블록의 실행 기록”을 분리해서 각각 인증합니다.

↗

⛁

Crash-safe vote / commit

투표 의도를 전송보다 먼저 저장하고, 확정 데이터는 synced atomic batch로 기록합니다.

막는 문제: 재시작 후 이중투표 또는 절반짜리 commit

자원 상한: 공격 비용도 합의 규칙의 일부

유효해 보이는 큰 데이터나 수많은 fork가 메모리·디스크를 끝없이 차지하지 못하도록 경계를 둡니다.

Block payload10 MB
Sync / TCP response32 MiB
Snapshot JSON64 MiB

막대 길이는 상대적 시각화이며 목표 사용량이 아닙니다. ActiveSync window는 최대 1,000 blocks, 누적 128 MiB로 제한됩니다.

Speculative state: 확정 전 후보를 안전하게 다루기

HotStuff는 여러 view와 늦게 도착한 QC 때문에 확정 전 branch를 잠시 보관해야 합니다. Block·pending·journal 저장에는 개수·깊이·byte 상한과 진행용 여유 공간을 둡니다.

Application state는 copy-on-write를 사용해 branch마다 전체 장부를 즉시 깊은 복사하지 않고, 실제로 바뀐 부분만 분리합니다. 다만 모든 application candidate를 합친 hard byte cap은 아직 후속 과제입니다.

비유: 문서 초안마다 책 전체를 복사하지 않고, 원본을 함께 보다가 수정한 페이지만 별도 복사하는 방식입니다.

05 · HYCK와 staking

보상은 새로 찍지 않고, 이미 발행한 reserve에서 이동한다

이번 PR은 native token과 거래 collateral을 분리하고, staking voting power·보상·공급량 보존을 하나의 결정적 회계 규칙으로 묶었습니다.

Genesis에서 정확히 10억 HYCK

611.12M초기 배분 가능
388.88Mreward reserve

6 decimals: 1 HYCK = 1,000,000 base units. Validator bond와 사용자 allocation은 이미 발행된 treasury 몫에서 옮깁니다.

liquid + bonded + unbonding + pending rewards + reserve = 1,000,000,000 HYCK

Reward clock

총 eligible stake가 커질수록 APY가 낮아지는 정수 inverse-square-root 곡선을 사용합니다. 400M HYCK가 stake된 지점의 연 환산 anchor는 2.37%입니다.

매 block경계 확인은 O(1)
90분reward accrual
24시간자동 compound

Reserve가 소진되면 지급은 0이 되며, 빚이나 무담보 신규 mint를 만들지 않습니다.

Voting power

Whole bonded HYCK를 voting power로 변환합니다. Active set은 stake 내림차순 최대 21명입니다.

Curated epoch 0

현재 genesis에 넣은 소수 validator가 운영합니다. 2~3개로 시작할 수 있지만, 3 equal-power 구성은 한 노드 장애도 견디지 못합니다.

Dynamic PoS는 staged

다음 top-21과 transition proof 구조는 준비했지만, historical committee와 원자적 context 교체 전에는 활성화하지 않습니다.

주의: Slashing은 application의 stake를 treasury로 돌릴 수 있지만, 현재 static epoch-0 consensus 위원회의 voting power를 즉시 낮추거나 validator를 퇴출시키지는 않습니다.

07 · 현재 수준을 정확히 말하기

완료, 준비, 미완료를 섞지 않는다

“코드가 존재한다”와 “실자산 mainnet에서 안전하다”는 전혀 다른 주장입니다.

✓ 로컬/dev에서 동작 확인

  • 통합 hl-node local runtime
  • 싱글노드·Docker 4-validator
  • Static curated stake-weighted consensus
  • Canonical EIP-712 web signing
  • 거래 gossip·bounded rebroadcast
  • State root + Commitment v2
  • Atomic RocksDB commit/recovery
  • Finalized tx receipt 조회·WS 알림
  • Finality-proof HTTP startup block replay
  • 고정 공급 HYCK reward accounting

△ 구조만 준비 / 제한적

  • 다음 top-21 validator update 산출
  • Bounded epoch transition proof staging
  • Application-level slashing·jailing
  • 64 MiB bounded snapshot 저장 형식
  • Legacy agent delegation 경계
  • Indexer가 읽을 receipts/events 저장 구조

✕ 출시 전 반드시 필요

  • Permissionless committee 전환 활성화
  • Historical committee·key rotation
  • 완전한 snapshot manifest/chunk proof
  • Indexer bounded range/inclusion proof API
  • Ethereum bridge proof·reorg·pause
  • HSM/key custody와 genesis ceremony
  • Upgrade·telemetry·incident runbook
  • WAN chaos/long-run/load 검증
  • 독립 consensus·crypto·회계 감사

08 · 현실적인 다음 순서

쇼케이스에서 공개 testnet으로 가는 길

기능을 더 붙이기 전에 신뢰 경계를 완성하는 순서입니다.

Curated testnet 운영 검증

여러 host·region에서 장시간 실행하고 rolling restart, 느린 노드, 지연 QC, network partition, Byzantine 입력을 재현합니다.

위원회 전환을 원자적으로 활성화

Historical committee registry, transition certificate, key entry/exit/rotation, evidence hold를 한 번에 완성합니다. 일부만 켜면 오히려 위험합니다.

데이터 소비와 동기화 계약 완성

Authenticated snapshot chunks, multi-peer failover, indexer range/cursor API와 receipt/event inclusion proof를 추가합니다.

실자산·운영 보안은 별도 gate로

Ethereum testnet bridge proof부터 시작해 reorg/replay/pause/accounting을 검증하고, HSM·업그레이드·모니터링·독립 감사를 통과한 뒤에만 mainnet 후보로 올립니다.

최종 판단: PR #2는 “기능 데모가 되는 코드”를 “합의된 상태와 확정 결과를 설명할 수 있는 체인”으로 끌어올렸습니다. 하지만 공개 mainnet은 코드 기능 외에도 동적 위원회, 브리지, 운영 절차, 장기 검증과 독립 감사까지 모두 통과해야 합니다.

09 · 용어 사전

처음 보는 단어 빠르게 찾기

Canonical
여러 구현 중 체인이 진짜로 인정하는 단 하나의 규칙·경로.
Mempool
접수됐지만 아직 block에 확정되지 않은 거래의 대기실.
Nonce
사용자별 거래 순번. 같은 거래의 중복 실행과 순서 뒤집힘을 막음.
Validator
블록을 검증하고 투표하는 노드 운영자.
Voting power
합의 투표의 무게. 현재는 bonded HYCK 양에서 계산.
QC
엄격한 2/3 초과 voting power가 같은 결과에 동의했다는 BLS 집계 인증서.
Finality
해당 block이 합의 규칙상 되돌려지지 않는 확정 상태가 됨.
State root
전체 상태를 짧은 hash 하나로 요약한 지문. 한 값만 달라도 바뀜.
Receipt
한 transaction의 성공·실패, block 위치, 이벤트를 담은 확정 실행 기록.
PoP
등록한 BLS 공개키의 비밀키를 validator가 실제로 소유한다는 증명.
Epoch
같은 validator 위원회와 규칙이 적용되는 합의 기간.
Copy-on-write
복사본을 미리 전부 만들지 않고 실제 변경이 생긴 부분만 분리하는 방식.
